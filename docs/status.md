# Current state

Updated 2026-10-25. What Sealbook does today and its known limits. Every
measurement here was taken on synthetic data; no production archive or partner
data was used.

| Area | Implemented | Limits |
| --- | --- | --- |
| Framework | An app on the `stkit` 17 package: every module in `sealbook/` is an extension with `init_app`, settings live in `sealbook/settings.py`, templates and static files override stk's, and one migration, `sealbook_0001`, sits on stk's `stk_0001`. Its schema matches a database built by the earlier 28 revisions (column order aside), with the same policy, role and place kind rows. Dated revision names below, such as `20261029_agent_tasks`, name parts of `sealbook_0001` | A database built before the move to the stk 17 package is not upgraded; rebuild it |
| Standing questions | `agent_task` and deduplicated `agent_wake` (`20261029_agent_tasks`); local runs for the person who asked, evidence wakes, daily checks, coalescing, empty-result backoff, five-minute failure retry and pause after three failures or access loss. Two-pass screening and judgment use handles, validate citations, suppress repeated claim sets and retain deferred claims. Desk: ask, Check now, Stop/Resume, latest masked matches and check history. The full demo seed adds one fixed-output question to case-demo-02 | Access follows the existing active analyst/admin role and case existence; the app has no per-case access list. As with the intake brief, masking hides erased citations but stored output and raw model bytes remain. Browser behavior and live model quality are not yet verified |
| Custody | SHA-256/MD5 intake, acquisitions, signed statements, sealed runs and chain verification | Physical blob encryption and erasure remain incomplete |
| Trust | Pure gate, rebuildable tiers, signed human acceptance/rejection/undo | Similarity never grants factual acceptance |
| Integrity | Merkle batches, OTS/TSA receipt paths, partner root copies, offline package verifier | External service paths do not prove a configured or certified deployment |
| Intake | /ingest (Add evidence): pick a case or make one on purpose (typing never creates one), then stage files (drop, paste, choose, phone camera), links, web results from a case-level search, a spreadsheet or a voice note recorded in the browser (MediaRecorder). Each staged item has its own document type (a suggested type from mime, file name and sheet columns, marked as a suggestion; `POST /ingest/suggest`), sensitivity and origin over batch defaults, checked on the server against a fixed list. The browser takes each file's SHA-256 at once and the upload sends it; different bytes on the server record nothing (422) and a match is noted on the acquisition (`browser_sha256`). Staged rows become progress rows (fingerprint, stored, reading, claims, linked; captured first for web items) read from `GET /ingest/batch/<id>`, which now also gives per-item claims, document type, sensitivity, origin, the capture run, a duplicate's original (title, when, from where, case) and `waiting`: no model may read it (with the plain reason, sensitive items local only), or its reading is queued behind others of the same tool. Plain-words failures with Try again (`POST /ingest/run/<id>/retry`); the batch ends on the intake brief. Repeat bytes store nothing new; the upload is one more acquisition on that source's custody record. C2PA verification, URL recheck, image OCR, text extraction, page-located PDF text indexing and local audio/video transcription; `read_progress` per item for long reads; OCR and extraction run only when a route has a model (`MODEL_LOCAL` and friends, [operations.md](operations.md)); PDF pages with text get a claim extraction each; the evidence page's Queue processing names what it queued or the missing setting and shows each read's state until claims arrive | No automatic scanned-PDF OCR; Local extraction with gemma4 12B on a 16 GB laptop takes minutes per page and often repeats one claim until the context ends on list-like pages (see verification); the page keeps the batch only while it is open (Inbox and the Desk keep the brief); the parts of a capture other than its page, picture or video (screenshot, network log, other media) get no rows; a pasted link is fetched by the server, not rendered by the capture browser; an item that arrived while no model could read it is not queued again on its own |
| Cases | `case_record` (`20261028_cases`): id, slug, name, description, created_by, created_at. The slug is the investigation string acquisitions, datasets, findings and filters already carry, so existing data keeps working; the migration made one row per string in use (acquisitions, research switches, datasets) with no creator. `GET /api/cases` lists each with sources, people (the People list count), last added and recent origins; `POST /api/cases` creates one and answers 409 when the name is taken, or close to another (within two edits or contained) until the person confirms. Intake (`/ingest/file`, `/ingest/url`, research search and capture) refuses a case not in the table; the shell switcher and every page's case list read the table. Seeds create their case rows | No rename, archive or delete; no per-case access; new slugs equal the name as typed |
| People | Arabic/cross-script candidates, draft/factual tracks, "Sources disagree" listing each unresolved disagreement once with each side's value and source link (two same-day positions disagree only when they are farther apart than the larger place precision, the rule shared presence uses, and are not a last-seen and arrest pair), identity proposals, watchlists and source-backed actor embeddings; one label rule (`people.names`) for Desk, Discover, Stories, People, the palette and the sign dialog: the best name the reader may see from any linked record, else "Unnamed person N" with a lock; candidate duplicates show one line per candidate naming each matching name once (masked ones counted behind a lock), most agreeing fields first; a name match every other field contradicts shows last as "likely two people"; each fact links to its source title at the claim, the model only in a tooltip; the list and header say "joined from N records" only when N is above one; the People list, global search and the Watching picker show each person's dates, and tell apart only rows that read the same (one name, one dated range) by the first fact that sets each apart (`people.hints`: another case than the filtered one, then first source), with the id only when none does; the list, the person page and search count the same facts and documents (current, not rejected, no identity links), checked by `check_sense` | Embeddings do not merge identities |
| Located search | Original text offsets, Arabic passage normalization, exact identifier priority, PDF page preview and match labels | Candidate limits are bounded; no Arabic retrieval gold-set evaluation |
| Semantic search | One 768-dimensional EmbeddingGemma 2 space for text passages, actor profiles, images, PDF pages, video frames and audio windows; source-linked artifacts and signed recipe/reference provenance | Runs on local Ollama; measured only on the synthetic retrieval set, where scans rank weakest. Search leaves out leads more than 0.05 below the best similarity in the same answer and labels the rest close, related or loose (number in the tooltip); the cutoff and bands are set from the gold set, not calibrated |
| Index health | Bounded text/PDF/media continuation jobs, acquisition pagination, current-generation coverage and reference-vector drift refusal | Text chunk planning still reads the full source; coverage lists at most 100 sources |
| Transcription | `transcribe` tool: faster-whisper 1.2.1 with Whisper large-v3-turbo in the worker process, local route only (sensitive recordings qualify), queued for new audio and video by ingest and by `stk enrich`. VAD, word timestamps, language detection with Arabic when confidence is below 0.5. Each speech segment is a derived text blob located by `{"ms": [start, end]}`, indexed and embedded like page text; the full transcript is a derived blob that extraction reads when a model is configured. Runs read windows of `SPEECH_CHUNK_SECONDS` and continue from the last kept segment; a run also stops before its lease ends. Model revision, weights hash, runtime, device, compute type, language and probability are in the run and its output. No speech and no audio track seal as done with a note; a missing model or ffmpeg fails in plain words with Retry | Measured only on one 33 s synthetic Damascene clip (WER 0.22 after folding, dialect spelling normalised toward MSA); CPU only on Apple silicon; extracted claims span transcript characters, not ms |
| Deduplication | Image PDQ, timestamped video PDQ plus audio landmarks, audio offset alignment | Fingerprint decoding remains per file with a duration bound; thresholds are not calibrated probabilities |
| Sheets | CSV (UTF-8) and XLSX through /ingest: stored and hashed like any file, never read automatically. Before it is added, `POST /ingest/sheet/peek` reads the file on the page (nothing stored or logged): header row, title rows skipped, dropped columns, four rows and a field per column (remembered from a dataset in the case with the same columns, else suggested, waiting at most 20 s for the embedding model), and whether it reads as a list of people; columns the person confirms there are confirmed after upload and the rows queued (a sensitive sheet takes the logged reveal first). A person picks or names a dataset, the row identifier column and a field for every column (remembered per dataset; unfamiliar columns get top-3 EmbeddingGemma 2 suggestions from header plus 5 samples, each needing a click), checks the diff against the latest available version (new, changed, unchanged, missing, invalid for blank or repeated identifiers; only mapped columns count), then confirms. `extract_sheet` (same route policy as `extract`, one row per local call, thinking off on the local route) proposes name, sex, age, occupation, position and `event` claims (killed, missing, displaced, released, wounded, defected) pinned to cell spans; dates come from a deterministic table (Arabic and English month names, Eastern Arabic digits, day first) as full intervals, "unknown" undated; places go through `places.resolve`, unresolved stay open. `GET /api/sheets/<acq>/preview\|proposals`, `POST .../diff\|confirm`, `GET /api/evidence/<sha>/sheet` (sensitive sheets need the logged reveal). Measured once on `messy_people.csv` with local gemma4 12B (`acceptance/eval_sheet.py`): name 15/15, sex 8/8 with none inferred, age 12/12, occupation 13/13, event kind 8/8 plus 1 wrong event, date 13/13, place quoted 11/14; position props 11 supported and 5 unsupported (mostly `seen_at` from the place column); column suggestions top-1 right for 4 of 6 columns | The header is the first row of the first ten with at least two distinct filled cells and 60% of the fullest row near the top, so title rows above it are skipped and their row numbers kept; a column with no header and no values is dropped from mapping; any other column needs a distinct header; 20,000 rows and 200 columns per sheet; one dataset version per sheet blob; /ingest reopens only sheets added on that page, so an earlier version's stored diff counts are not shown anywhere; a changed row is read again in full, so its unchanged facts are proposed again against the new version; missing rows retract nothing; slow on a laptop (about 40 s per row) |
| Thumbnails | `thumbnail` tool (local, queued for every image, video, audio and PDF source, and by `stk enrich`): WebP 480 and 160 square tile with orientation applied and metadata stripped; video poster from the sharpest non-dark of four sampled frames plus a 12-frame strip with timestamps; PDF first page plus up to 50 small page renders; audio waveform PNGs and peaks JSON. Runs seal tool version and parameters. `GET /api/evidence/<sha>/thumb?size=160\|480[&page=N]`, `/strip`, `/peaks`, `/thumbs` (analyst only; sensitive sources 403 `reveal_required` until revealed in the session; a source without a thumbnail answers 204 and lists never ask for text, web or sheet kinds; erased 404; a blob with no stored bytes (synthetic fillers) answers 404 `no_file`; `private, no-cache` with ETag) | Thumbnails are not logged as views; derivatives are linked by run manifest, not signed `derived_from`, so erasure hides them by source availability but leaves the bytes on disk; a source needs a rebuild run to change sizes; the place and incident evidence tables and the media connections on `/evidence` pass no lock, so an unrevealed sensitive tile there still answers 403 in the console |
| Findings | `stk discover --investigation X` queues a sealed run that proposes signed shared-presence and candidate-incident findings from accepted or corroborated, dated, place-resolved claims; shared presence also joins two places whose centroids lie within the larger of their two precisions (`ST_DWithin`), and its reason names the distance and both precisions ("Both held 1.2 km apart, at Branch 999 and Al Jadida, in July 2013 (places known to within 250 m and 1 km)"), with each member's own place in the finding; keys salted with a stored deployment salt over kind, investigation, people, places and month suppress open, accepted and rejected sets, and each kind keeps at most `FINDINGS_PER_KIND` (20) open per investigation, the rest deferred by rank | Same event in other words, same person and cross-media findings are not built; a place without a precision (admin areas) never joins by distance; candidate incidents still need one place |
| Places | PostGIS 3 (`20261026_postgis`): `place.geom` (point, line or polygon, SRID 4326) with generated `centroid` (geography), `lon` and `lat`, GiST indexes; `precision_m`, `geo_source` (geonames, cod-ab, geoboundaries, analyst, exif, c2pa, derived) and `geo_statement_id`; a `place_kind` ladder table (admin kinds per country and level, settlement and facility kinds, each with a default precision); `place_name` with `kind`, `valid_from`, `valid_to` and `source`. `stk places boundaries <COD-AB GeoJSON zip>` imports OCHA COD-AB boundary sets (versioned, licence and attribution stored) and sets every place's `admin1_id` and `admin2_id` by point in polygon; name resolution scopes by that governorate when a place is inside one, else by the gazetteer's | Names valid over time are stored, not yet used by resolution; no prop records a facility's operator, so place pages show no operator over time; analyst-set geometry is not yet signed (person-created places carry no statement); the newest boundary set is used for every date |
| Maps | `GET /api/map/tiles/<z>/<x>/<y>.mvt?investigation=&from=&to=&tier=&lens=&ref=` and its TileJSON (`/api/map/tiles.json`, boundary credit): layers `points` (server clusters of 5 x 5 cells per tile below zoom 11, ids of the first 200 members), `sequences` (from zoom 8), `uncertainty` (from 8), `footprints` (from 10) and `admin`. Claims are the visible ones (value kept, source available, current, in the filter, own or document date) resolved by a set-based SQL twin of `resolve.resolved`, which the resolution tests check against the Python path. A model per reader and query is kept in process for 30 s while the chain head, or the map-relevant statement and acquisition counts, stay the same; responses are `private, no-store`. The worker telemetry page and the person map draw points and sequences from the tiles; the case map and story map draw boundaries, uncertainty and footprints from them under their own places. The person map labels each resolved place once with every spelling joined ("Aleppo / حلب"), as Stories does. Measured on 100,000 synthetic claims at 2,000 places (`python -m sealbook.maps.scale`, throwaway database, local laptop): model build p50 1.17 s, p95 1.20 s; warm tiles p50 39 ms, p95 69 ms (z5 p95 145 ms) | One process only (memory cache); the first map view after a map-relevant write waits for a model build; low zoom tiles carry up to 200 ids per cluster; sequences are per raw subject, not per identity cluster; no heat layer and no unresolved-names list in the tiles (both maps keep theirs from JSON) |
| Basemap | `stk basemap` extracts a Protomaps PMTiles basemap (OpenStreetMap, ODbL) with the `pmtiles` CLI into `instance/basemap/syria.pmtiles` (default bbox 34.9,32.0,42.6,37.6 to zoom 14: 217 MB from build 20261023), with a sidecar of build, bbox, size and sha256. The app serves it by range requests (`/api/map/basemap.pmtiles`, signed-in readers, `private, max-age=86400`); the case map, telemetry, story and evidence maps draw earth, water, land use, roads, buildings and boundaries from it with OpenStreetMap credit, and keep the Natural Earth outlines when it is absent | No labels (no glyph server); refreshing it is a manual rerun |
| Evidence location | `photographed_at` and `filmed_at` props on a blob: point geometry as decimal strings, `precision_m`, `method` (exif, c2pa, analyst), optional `bearing` and `landmarks`. The local `geotag` tool, queued at intake for images and video, reads EXIF GPS (with stated error and image direction), a video container's ISO 6709 tag and the C2PA `stds.exif` assertion, and writes unconfirmed agent proposals, never finer than 50 m. `GET /api/map/evidence/<sha>/locations`; `EvidenceLocation` component draws point, circle and bearing on the offline basemap | No analyst geolocation form yet; a human-signed location is accepted on signing like any human statement, so analyst geolocation needs a review path before it is built; location of segments within a video is not read |
| Discover | `/discover`: open findings strongest first, a reason sentence ("Both held at Branch 999 in July 2013"), a strength band (never a probability) and one card and checklist row per person listing each supporting claim with its span; the sign button states what one gesture records; a shared presence and a candidate incident over the same people, place and month name each other ("also a candidate incident"); a finding with any member erased or unavailable is not shown; opening one writes an access record, which ends "new since you last looked" for that analyst. Accept is a checklist (members, roles default unspecified, new incident title or an existing incident) signed by one passkey assertion over all its statement hashes (`POST /api/review/findings/options`, then `/api/review/commit`): incident, place and window, involved, supported by and the review, each with one gesture id, and the key moves to accepted. Reject is signed the same way and keeps the reason. `POST /api/review/undo` retracts a whole gesture or chosen statements and reopens the finding. Ask a colleague uses review requests; bulk assign uses `finding:<key>` subjects. Any review of a finding statement, by either path, moves its key | Excerpts and names from a sensitive source show only after a logged reveal on the evidence page; a candidate finding has no "open as story" link (the story view takes accepted incidents and shows pending findings as bands) |
| Stories | `/stories?lens=person|group|incident|place|filter&ref=&investigation=&from=&to=` and `GET /api/stories` (`sealbook/stories`): rows of people with tier textures, gaps labelled "N days, no evidence" when longer than 30 days, places in two positions on one day compared by resolved place (two spellings of one place never disagree), accepted incidents as outlined bands and pending findings the reader may fully see as hatched bands that open their member checklist and link to Discover; a MapLibre map of resolved places numbered in time order joined by sequence lines (not routes), unresolved names listed under it with GeoNames and Natural Earth attribution; one scrubber with play drives both; an evidence strip with thumbnails, the selected point's statement and its excerpt (segment link, page link for scans). Erased or masked values never become points; every read writes one access record per person row. Save keeps the query only (`saved_story`, per user); Package creates a brief with one cited sentence per row from accepted or corroborated points. The person page shows the same timeline compact with an Open story link | Pending findings come from `findings.queue`, so a story inherits its all-members-visible rule; the evidence page has no deep link for a whole-item span (`?segment` needs an indexed text segment); every story read logs one access per row, which grows the ledger quickly for a large filter lens; no time-window picker in the UI (URL only) |
| Case map | `/case-map` (rail "Case map"; `/monitor` redirects there, and its old side-panel links go to `/monitor/runs`), `GET /api/case-map?investigation=`, `/api/case-map/path?investigation=&from=&to=` and `/api/case-map/news?investigation=` (`sealbook/casemap`). One case at a time: a row per person cluster from the story view's filter lens (same masking, erasure and per-row access record), a segment per located claim with tier texture and its place; held-together bands from discovery's `shared_presence` over the visible points of every tier (plus `near` places), dropping a band of only two records an open same-person proposal joins; silences from `stories.gaps` and "no record after" from the gap finder's `detect` (release and death close it; kept only when the last account is on the timeline); "possibly two people" for records an open same-person proposal joins (`read.links`). Rows by first seen or first place, filter by place. A MapLibre map on the basemap: places sized by people in the window, approximate places (coarser than 250 m or no precision) faint and at least as wide as their uncertainty, moves as arrows, dots on them only while playing and never with reduced motion. One slider with play and a month, quarter, year or whole-case window drives both; a place or band opens who was there, arrived from, left to and no record after, each line linked to `/evidence/<sha>` at the claim, and a band discovery already proposed links to its finding. Path: breadth-first, at most 8 links, over held at, transfer, held together, named in the same source, family relations and open same-person proposals; each step a sentence with its sources, a place step whose two stays do not overlap marked weak with how far apart, unconfirmed steps said so; the people on the answer are logged as viewed. Case news: intake batches (sources, how many people they name, how many were already in the case), finished brief, linker, standing, contradiction and gap runs counted, and human decisions on claims and findings by kind, newest first, reread on each run event from the monitor stream. `/monitor/runs` keeps the worker telemetry, admins only. `tests/test_casemap.py` | Bands rest on any tier, so an unconfirmed claim can make one (its texture says so); people with no located claim are not on the map or in the path; same-source steps link the source, not the claim; the news counts agent output, it does not quote it, and a gap or contradiction run's count is shown to everyone in the case although the report is its requester's; a whole-case path rebuilds the case each time; place names are not drawn on the basemap (no glyph server), so labels are HTML; the review and documents panes left this page (Review and Sources do that job); the sense check on the copied demo database flagged one Inbox line (the actor chip prints the model name), outside this change |
| Sources | `/sources` and `GET /api/sources`: one row per acquired blob, server paged (per_page up to the platform cap of 100), sort on every column, filters for type, C2PA, sensitivity, open findings, assignee, collector, acquisition dates, free text and intake batch; claims, findings, C2PA, run state and assignment are SQL aggregates, page-only unless a sort or filter needs them; bulk assign through `/api/assignments/bulk`, request review of the selection's open proposals (`POST /api/sources/review`, dry-run count first, at most 200, one notification), workload strip, thumbnails in the table and grid from `/api/evidence/<sha>/thumb` with sensitive media hatched until a logged reveal (Desk recent evidence carries the same `revealed` flag, so its tiles never ask for an unrevealed source). `python -m sealbook.sources.scale` seeds synthetic sources into a throwaway database; at 20,000 sources every measured page took 83 to 264 ms of query time | No "add to story" from a source selection (a group lens is a selection of people, not sources); stories open from a person, group, incident, place or filter lens; a session keeps only the last 8 reveal grants; filler rows from `sealbook.sources.scale` carry a synthetic chip and have no file |
| Review | `/review` is the decision workspace (Inbox is for conversation). Chips: Asked of me (requests to me and open statement assignments to me), Sent by me, All open (unconfirmed claims by use) and Findings, due first. Each row is the claim as a sentence (person, prop, value, date), its source thumbnail, file and place in it (region on page, page, second, cell, characters), the proposer (person, agent or run) and who asked whom, when and the due date, with its tier texture; `GET /api/review/queue?box=mine\|sent\|open` builds a page in a fixed number of queries. The pane (`GET /api/review/claim/<id>`, `GET /api/review/request/<id>` for `?request=` links, `?statement=` selects too) shows the evidence at the span: image crop with the box plus the image viewer, PDF page with the line found, audio and video at the second, sheet cell, text with the span marked; the checks in plain words, run provenance and evidence kinds, other claims on the same person (identity cluster) and prop with agree or differ, the thread with a reply and Open in Inbox. Same-person proposals compare both people field by field from their basis statements, shown as cards. Accept (a), Reject with reason (r), Correct (e, a superseding proposal sent to a colleague) and Ask (s); decisions show the rows the passkey signs (`rows` in the staging reply) before the prompt; Undo after a decision or later from My decision. j, k, Enter and x (select, then bulk assign). A person without a passkey gets 409 `no_passkey` with a setup link that returns to the page (`/wan-register?next=`) from every staging route, after the request is authorised | Analyst/admin access model remains; no investigation ACL; live delivery is process-local. Values stay masked by the server rule until the source is revealed. When a decision rests on sensitive sources (its own, an identity proposal's basis, the other recording, the corrected claim), the pane names them and one action, Show the sensitive values for this decision (`POST /api/review/claim/<id>/reveal`), runs the evidence page's logged reveal once per hidden source; Accept and Reject stay disabled until then. Masked list rows read "Name from a sensitive source" unless another readable spelling exists (`people.names`). A session keeps only the last 8 reveal grants, so a decision resting on more than 8 sensitive sources cannot be unblinded in one session. Correct is not a decision: the original stays pending until the correction is signed. The Findings chip accepts with every member and unspecified roles; changing members or roles stays in Discover. Agents record no reasoning yet, so the pane says so. Audio claims point at transcript characters, so their second comes from the transcript timeline |
| Inbox | `/inbox` (rail and mobile bar): one list, newest first, of review requests asked of the analyst or sent by them, threads they are in (replies, @mentions), open work assigned to them with due or overdue, decisions on their requests and finished intake, with filter chips and unread state from stored notifications (selecting an item marks its notifications read through `POST /api/notifications/read`). The right pane shows the thread: the claim as a sentence, its source thumbnail and span, the request, comments with authors and times, a reply box with @mention suggestions, and Decide in Review (`/review?request=`) for the reviewer; decisions stay in Review. Keys j, k, Enter, c and r; single pane with back on mobile. Notifications about requests, replies, mentions and decisions link to `/inbox?item=request:<id>`; Desk mentions and replies open `/inbox?item=note:<id>`. No new endpoint: the page merges `/api/notifications`, `/api/collaboration/requests` (both boxes) and the assignments in `/api/desk/needs` | Reads the newest 100 notifications and 100 requests per box in the browser; a server inbox query is needed past that. Same-person claims show no names (naming them would need a logged person read). An assigned-work notification folds into the assignment rows written within a second of it; one that matches no open assignment stays a row of its own. Mentions notify only the thread's people and admins, though suggestions list every analyst |
| Source support | Accepted same-recording links collapse origins; corrections remove old support; undo reprojects and refreshes actors | Contains/related links do not collapse whole recordings |
| Evidence page | `/evidence/<sha>` per source: image, PDF (pdf.js), audio, video and sheet viewers (cells with each claim marked, `GET /api/evidence/<sha>/sheet`), claims with tier textures, copies, relations (same person with each side's readable name and the basis count, recorded excerpts, same place as one row per other source and place with the props on each side and a claim count, places named by more than 3 other sources folded behind one line, then nearest by meaning with a band word and the cosine distance only in the tooltip; at most 20 same-place rows), metadata and custody, thread drawer, passkey decisions, side by side; sensitive items ask once, others show with a logged view | Strength bands uncalibrated; no incidents listed |
| Privacy | Logged reveals of sensitive sources, logged views of all others, and byte verification for source/PDF/media previews; erasure removes search projections and blocks derived artifacts, including shared parents | This is access exclusion, not physical deletion of stored bytes |
| Web research | Built, off until `BRAVE_API_KEY` is set; capture also needs Chromium on the server (`uv run playwright install chromium`). Research drawer on the person page and the evidence intelligence panel, and a case-level search on Add evidence (scope `case:<slug>`, proposals from the case's shareable names with a place or year, each query logged on the case, captures queued into the page's intake batch with each result's own type and sensitivity): proposed queries from accepted or corroborated names, places and years from ordinary sources in cases that allow research (gazetteer names for places, place and month for incidents), edited by the analyst, who sees exactly what is sent; Brave web, image and video results grouped by type with domain, date, server-fetched thumbnail, why suggested and "already in this case" (same link captured, or thumbnail PDQ near a held picture). Every Brave request is an `access` statement (`action: research`) written and committed before it leaves. Sensitive or switched-off cases refuse (`POST /api/research/case`, admin); hourly limits per person. Copies of one page found by several queries merge into one result listing those queries; a result that does not mention the subject sorts below the rest and reads "may not be about <name>", and when none does the drawer says so and names the closest weak result; an optional from/to date window goes to web search only. Add as evidence queues a sealed `capture` run: one visit by a local headless Chromium (final URL, status, rendered HTML, full-page screenshot and a JSON network log of document and image requests, each hashed and stored), the result's image and up to 8 media on the page, yt-dlp (pinned) for a video result, each file through normal intake as the analyst's acquisition with method and the query's access statement id; progress through the intake batch (`GET /api/research/batch/<id>`). A login form, a bot check, an error status, a download, a private address on any redirect hop or a video needing an account fails the capture in plain words. YouTube is a fourth kind beside pages, images and videos and needs no key (search works without `BRAVE_API_KEY`): the same proposed and typed queries, preview, access statement (`provider: youtube`), hourly limit and case switches; yt-dlp `ytsearch` in flat mode gives title, channel, duration, views, a server-fetched thumbnail and an approximate date ("about 2016"), sorted earliest first by default with a switch to relevance. The first 5 videos (by grounding, then relevance) have their subtitles read without media in one 30 s budget: manual Arabic or English, else the automatic captions in the spoken language, never a machine translation; each recorded spelling of the subject (a typed query listens for its own words) is matched through the Arabic normaliser across a cue and the next, and the line shows with a link to that second. A subtitle match grounds the result and the upload date replaces the estimate. One video found by several queries is one result. ## Contradiction hunter (2026-10-24)

Implemented a manual case report (`contradictions`, `sealbook/agents/contradictions.py`),
with a panel under Sources disagree on the person page. It reuses the person
projection's disagreement builder, the brief's single-valued fields and the
linker's conflicting fields, and their shared value comparison. Different birth
date precision alone is not a disagreement. It also compares two person records
that an open (unreviewed) same-person proposal joins, even within one source, and
reports such a pair as possibly two people; each side names its record. Without
this the demo case had no candidate, as its cross-record disagreements sit only
behind open proposals. Accepted claims rank first, then
source count. Up to 24 candidates are read, four per call, within the worker's
time budget; the report counts deferred work. Each explanation and draft question
cites at least two sides from one candidate. Invalid citations, handles in prose
and sensitive values without their citation are dropped and counted. Claim sets
already reported by a finished run for this case are not reported again.

The run acts for the requesting person, uses the local route and `AGENT_MODEL`,
and writes only its reading access record to the ledger. Its report is a sealed
JSON output with a proposed count and a plain reason when empty. The latest report
is masked for the reader as the intake brief is: a sensitive source needs a reveal;
rejected, erased, replaced or unavailable claims remove the item. The API starts
a run (`POST /api/agents/contradictions`), reads the report (`GET` with
`investigation`), and exposes status only to the requester or an administrator
(`/api/agents/contradictions/runs/<id>`). A case lock prevents two manual checks
from being queued together. The panel shows source titles and dates, the
explanation, and a question with Copy question. It sends no message.

Offline checks cover citation boundaries, leaks, repeat suppression, deterministic
fixed output, value precision, place identity, ranking, caps and time deferral.
The existing brief and person disagreement pure tests also pass. The component
template compiles offline and its start, completion and empty-state flows pass.
Postgres tests in `tests/test_contradictions.py` cover the fixed run, read-only
ledger behavior, repeat runs, sensitive reveal, later rejection, and manual API
guards; they pass on PostgreSQL with the full suite. A switch on the panel keeps
the check running as evidence arrives through the agent task queue. No live model
quality is established. Stored report and raw-output bytes retain the brief's
physical-erasure limitation.

## Gap finder

Gap finder is implemented in `sealbook/agents/gaps.py`, registered as `gaps`, with
manual `GET` and `POST /api/agents/gaps` routes and a Gaps panel on People and
person pages. It detects silences longer than 60 days after arrest, detention or
a missing account, ending at later evidence or a sighting. A typed release or
death closes that period without a gap proposal. The last detention or last-seen
account also gives an open end. Uncertain dates use the previous claim's latest
date and the next claim's earliest date. Open windows use `[date, null]`, so the
same open end is not proposed again each day.

Candidates and leads are built before model calls: up to 12 gaps per run, longest
first, four per call within the worker budget, with up to five unlinked sources
whose claims put another person at a resolved bracketing place wholly within the
gap. Colleagues come only from the cited claims' public review and collection
attribution, excluding the requester. Private review requests are not read.
Every suggestion must cite all supplied bounds, source leads and any supplied
name. Invalid citations, URLs in searches, handles in prose and uncited sensitive
values are dropped and counted. Runs store suggestions and an explicit outcome,
and write only their access record to the ledger. Earlier reported windows for
the same requester are suppressed until their bounds change. Reads remove items
with unavailable claims and lock the whole suggestion on unrevealed sensitive
sources. The panel states each window with both ends and its length ("No record
after" for an open end), lists other people's lead claims apart from the person's
own, uses the app's field labels, folds consecutive locked suggestions into one
line per sensitive source, and keeps two records an open same-person proposal
joins next to each other with a note. A later check that finds only what was
already reported keeps the earlier report on screen (also for contradictions).
Search in research fills the existing drawer; only its Send button
performs a search. There is no standalone research page or query URL parameter.

All 18 offline checks pass in `tests/test_gaps.py`: gap rules, citation and search
validation, run limits, access logging, requester checks, Vue template compilation,
person filtering and research prefill without sending a search. The new
PostgreSQL tests cover the fixed-output run, cited source lead, colleague
attribution, access-only ledger writes, duplicate suppression, masking, reveal,
rejected basis claims and manual route ownership, off and busy states. These
database tests pass on PostgreSQL with the full suite. A switch on the panel keeps
the check running as evidence arrives through the agent task queue. No Ollama run
has been measured. The existing person map's phone overflow was
not changed; the new panel wraps its text and has no fixed minimum width.
Live model phrasing quality and the new panel at 390 px remain unverified.
As with the intake brief, erasure removes suggestions from the view through their
citations; sealed report and raw response bytes remain.
