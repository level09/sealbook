# Lessons

- 2026-11-01 | `stk smoke` timed out on a page that opens an EventSource on load under Playwright 1.60 (networkidle never reached) | require playwright>=1.64.1, which does not count the stream, and open streams at once | stk (covered upstream: stk requires playwright>=1.64, 2edbba4)
- 2026-11-01 | a `stk run` started in the background on a taken port exits with code 3 and logs "Address already in use" while the old server keeps serving | check the log or the port's listener before assuming edits were applied | stk (covered upstream: exits naming the pid, b29ccf0)
- 2026-11-02 | on 17.4 a test calling `broadcast(msg, "fixture-target")` raised ValueError: int() of a non-numeric user id | test the bounded per-socket queue through `stk.websocket._deliver`; app code already passes numeric ids | stk (expected: user_id must be numeric; worth a clear error message naming the argument; handled in 17.6.1)
- 2026-11-02 | after 17.3.2 a test GET of `/static/css/app.css?v=abc` returned `no-cache`, not immutable | request the file's real versioned URL from `assets.asset()` | sealbook (stk caches only a matching version, as intended)
- 2026-11-02 | sealbook models Notification and McpToken share names with stk models; a string `relationship("Notification")` would match both and fail every mapper at startup | name them by class in relationships | sealbook (stk 17.4.2 stopped using string names in core)
- 2026-11-04 | on 17.9.5 `stk smoke` hung partway through the dark pass on whichever page was current (/incidents dark, /ingest/ dark), every request including static files timing out | the smoke server's stdout/stderr pipe was never read and its access log (~97 KB for 69 visits) filled the 64 KB buffer; upgrade to 17.9.6, which writes it to a temp file | stk (fixed in 17.9.6)
- 2026-11-10 | on 17.10.0 stk's 401, 404 and 500 pages extend layout.html with no `js` block, so nothing mounts and `v-cloak` leaves them blank; a sign-in form posted with an old CSRF token landed there as a blank 400 | the app layout ends with a default `js` block that mounts a bare app, and a 400 handler in `sealbook/shell` sends a form posted with an old token back to its page with a fresh one (stk could do both: mount on error pages, redirect on "Invalid CSRF token") | sealbook
- 2026-11-11 | stk 17.11.0 mounts on its error pages and sends a stale form token back to its page itself | dropped the default `js` block in `templates/layout.html` and the 400 handler in `sealbook/shell`; the two tests in `tests/test_security_compatibility.py` stay | sealbook
- 2026-11-11 | on 17.11.0 `netguard.pin` connects to `sorted(addresses)[0]`, and as strings 2600:... sorts before 3.x, so a dual-stack host is pinned to IPv6; in a container with no IPv6 route every fetch fails with ConnectError and `_thumb` hid it (no web thumbnails on production) | `dns_opt: no-aaaa` on the app containers in docker-compose.yml; stk could prefer IPv4 or try each checked address | sealbook
- 2026-11-11 | `SECURITY_POST_LOGIN_VIEW` defaults to `/dashboard`, stk's user-count page, so an app that replaces `/` still lands sign-ins there; set `SECURITY_POST_LOGIN_VIEW` and `SECURITY_POST_CONFIRM_VIEW` in the app's Config
- 2026-11-11 | on 17.11.0 `auth_required` redirects every signed-out GET to `/login?next=<path>` and the form stores that as `security_next`; an EventSource or XHR that outlives its session follows the redirect, so the next sign-in within ten minutes lands on `/api/live` (a 406 JSON page) | a `before_request` in `sealbook/shell` answers 401 to a GET of the sign-in form whose `Sec-Fetch-Mode` is not `navigate`; stk could do the same, or answer 401 without a redirect when the request is not a navigation | sealbook
- 2026-11-14 | stk 17.12.1 pins IPv4 first in `netguard`, and quart-security 2.2.1 answers 401 instead of a sign-in redirect to a request that is not a navigation | dropped `dns_opt: no-aaaa` from docker-compose.yml and the sign-in form guard in `sealbook/shell`; tests patch `netguard.resolve`, now public | sealbook
